# LuxGen Deployment — Issues Log, Optimizations, and Standard Workflow

This document consolidates every deployment-blocking issue found during the AWS free-tier + Vercel rollout, what was fixed, what's still open, and the standardized process to follow for future deploys on either side (API on EC2, web on Vercel). Read this before touching the deploy pipeline — it exists so the same bugs don't get rediscovered from scratch.

## Part 1 — Issues found and fixed

**Unrelated packages blocking both images.** The Dockerfile originally ran one `npx turbo run build` covering the entire monorepo, so a real TypeScript error in `packages/mcp-core` (against the MCP SDK's newer request-handler types — unrelated to this deploy work) failed the whole pipeline, blocking both `api` and `web`. Fixed by giving `api` and `web` independent Dockerfile build targets (`builder-api`/`runner-api`, `builder-web`/`runner-web`) that each scope their `turbo run build` to only their own real dependency graph via `--filter`. Neither app actually depends on `mcp-core`, `mcp-server`, `agent-worker`, `mobile`, or `native-ui`, so none of those need to compile to ship either image.

**EC2 disk too small.** The instance's root EBS volume was provisioned at only 8GB, and Docker's build cache alone was consuming 2.36GB, leaving it dangerously close to full. Free tier includes up to 30GB of EBS at no cost — the volume was resized to 30GB (`growpart` + `xfs_growfs`, no reboot needed). This should be the default size for any future free-tier instance in this project, not an afterthought.

**No swap, or swap lost after instance changes.** A 1GB swapfile was created but EC2 doesn't persist `swapon` across reboots unless added to `/etc/fstab` — it silently went back to 0B active at least once. Fixed by adding the swapfile entry to `/etc/fstab` so it survives reboots. Standard first step for any t3.micro-class instance running Node builds: 1GB+ swap, persisted.

**Node/V8 heap ceiling crash, not a real OOM.** Compiling `apps/api` (the heaviest package — Express, Apollo, Mongoose, Stripe types, GraphQL tooling all type-checked together) crashed with "JavaScript heap out of memory" after 8+ minutes, even though the OS still had RAM and swap available. V8 self-limits its heap based on detected system memory and gives up before actually exhausting what's available. Fixed with `ENV NODE_OPTIONS="--max-old-space-size=768"` in the `builder-api` Dockerfile stage, explicitly raising V8's own ceiling to match what the instance can actually provide.

**Internal packages `require()`-crashing at runtime.** All of `agent`, `auth`, `automation-flow`, `billing`, `config`, `core`, `db`, `storefront`, `utils` had `"main": "src/index.ts"` in their `package.json` — pointing Node's module resolution at raw TypeScript source. This compiles fine (tsc type-checks the source directly) but crashes at actual runtime with `SyntaxError: Unexpected token 'export'`, since plain `node` can't parse TS/ESM syntax. Fixed by pointing `"main"` at each package's real compiled output (`dist/index.js`, confirmed via each package's own `tsconfig.json` `outDir`).

**Regression from the fix above.** The first pass also changed each package's `"types"` field to `"dist/index.d.ts"` — but `tsconfig.base.json` never sets `"declaration": true`, so no `.d.ts` files are ever generated in this repo. That broke `@luxgen/agent`'s build with `TS2307: Cannot find module '@luxgen/config'`, since tsc resolves cross-package *type* information through the `"types"` field. Corrected by reverting `"types"` back to `"src/index.ts"` (real source, always available) while keeping `"main"` on the compiled `dist/index.js` — these two fields serve different consumers (tsc vs. Node) and can legitimately point at different files.

**`apps/web` has the identical latent bug, not yet triggered.** `apps/web` also depends on `@luxgen/config`, `@luxgen/db`, `@luxgen/billing`, `@luxgen/utils`, but none of them are in `next.config.js`'s `transpilePackages` list — meaning Next.js expects them pre-compiled, exactly like `apps/api` did. The root `package.json`'s `"build:web"` script was `turbo run build --filter=@luxgen/web` (no dependency-inclusion suffix), so it never actually built those dependencies first. Fixed the filter to `--filter=@luxgen/web...` (the trailing `...` is Turborepo's syntax for "this package plus everything it depends on"). Without this fix, the first real Vercel deploy would have hit the same "Cannot find module" crash currently affecting `api`.

**Git shell-session pitfalls (process, not code, but cost real time).** Multi-line command pastes starting with `sudo su - ec2-user` unreliably execute the following lines in the wrong shell; inline `#` comments break on zsh, which doesn't strip them in interactive mode by default; `git config --global --add safe.directory` is needed whenever a directory's owning user doesn't match the shell's current user. Standing rule going forward: run directory/user-switching commands alone, wait for the prompt, then paste the next block separately.

## Part 2 — Still open (tracked, not blocking)

`packages/ui`'s build script is `echo 'Skipping UI build due to TypeScript errors'` — a placeholder, not a real build. If `ui`'s `"main"` is ever changed to point at `dist/`, this will break immediately since no `dist/` is ever produced. Leave `ui`'s `main`/`types` on `src/index.ts` until this is actually fixed.

`packages/test-harness` has no `"build"` script and no `dist/` output at all. It's listed as a real (not dev) dependency of `apps/api`, which is likely a workspace-declaration mistake rather than intentional — check whether any production code path actually imports it; if not, move it to `devDependencies`.

`apps/api`'s `build-tolerant.js` wrapper still tolerates 43 pre-existing TypeScript errors (mostly Mongoose 7.x type-definition gaps in `packages/db`). This is a deliberate, documented, regression-guarded unblock — not a new issue — see `docs/CODEBASE_ARCHITECTURE_REVIEW.md` for the retirement plan.

`native-ui`, `design-tokens`, `types`, `mobile` were not audited for the same `main`/`types` runtime bug, since nothing currently depends on them at runtime the way `api`/`web` depend on the 9 already-fixed packages. Audit any of these the moment something starts actually importing them in a server context.

## Part 3 — Performance and reliability optimizations applied

Docker build scoped per-app via `turbo --filter` instead of building all 21 workspace packages for every image. `--concurrency=1` on the API's build so a 1-vCPU instance compiles one package at a time instead of several fighting over the same tiny RAM budget. `NODE_OPTIONS=--max-old-space-size=768` so V8 uses the RAM+swap that's actually available. 30GB disk instead of 8GB. Persisted 1GB swap. A safe build-then-swap deploy script (`scripts/deploy-api.sh`) that builds the new image before touching the running container, health-checks it, and automatically rolls back to the previous image on failure — replacing the old pattern of `docker compose up -d --build`, which could leave zero containers running if a build failed partway. A CI/CD pipeline (`.github/workflows/deploy-api.yml`) that compiles the image on GitHub's runners instead of the free-tier instance at all, using OIDC federation so no long-lived AWS credentials are stored anywhere.

## Part 4 — Deploying the frontend to Vercel

Code changes already made for this: `next.config.js`'s `output: 'standalone'` is now conditional on `process.env.VERCEL` (Vercel sets this automatically) — standalone output is a self-hosting/Docker concern and Vercel doesn't need it. Added `experimental.outputFileTracingRoot` pointing at the monorepo root, so Vercel's serverless-function file tracer correctly includes sibling `packages/*` files instead of stopping at `apps/web`'s own directory (a common, easy-to-miss monorepo+Vercel failure mode — it builds fine and then 404s/500s in production). Fixed `build:web`'s turbo filter per Part 1.

Steps to actually deploy:

Connect the GitHub repo in Vercel and set the project's **Root Directory** to `apps/web`. Override the **Build Command** to run from the monorepo root instead of just `apps/web`, so workspace dependencies get built first: `cd ../.. && npm run build:web`. Leave **Install Command** as the default (Vercel detects the root `package.json`'s `workspaces` field and runs `npm install` at the true repo root automatically once Root Directory is set).

Set these environment variables in the Vercel project's dashboard (Vercel doesn't read `.env` files from git or pull from AWS SSM — everything must be entered there directly): `NEXT_PUBLIC_GRAPHQL_URL` (pointing at the API — `https://api.luxgen.in/graphql` once DNS/TLS are live there, or a temporary `http://<ec2-ip>:4000/graphql` for early testing), `NEXT_PUBLIC_BASE_URL` (`https://luxgen.in`), `TENANT` (`demo`).

Add `luxgen.in` and `www.luxgen.in` as custom domains in the Vercel project's domain settings; Vercel will display the exact DNS records to create. Update those records wherever the domain's DNS is actually managed, verify with `dig luxgen.in +short` / `dig www.luxgen.in +short` that they resolve to Vercel's values, then disable (don't delete yet) the existing CloudFront distribution that currently serves the apex domain.

Update the API's `CORS_ORIGIN` (SSM parameter `/luxgen/prod/CORS_ORIGIN`) to match Vercel's deployed origin(s) — the browser will block cross-origin GraphQL requests otherwise.

## Part 5 — Standard workflow going forward

**Deploying an API change:** push to `main` touching `apps/api/**` or `packages/**`. If the GitHub Actions OIDC role is set up, this builds and deploys automatically. Until then, manually: SSM into the instance, `git pull origin main`, `./scripts/deploy-api.sh` — never raw `docker compose up -d --build`.

**Deploying a web change:** push to `main`. Vercel auto-builds and deploys on every push, with a preview URL on every pull request — no manual steps once the project is connected.

**Adding a new internal package that other packages/apps will `require()` at runtime:** give it a real `"build": "tsc"` script and a `tsconfig.json` with `"outDir": "./dist"`. Set `"main"` to `"dist/index.js"`. Leave `"types"` on `"src/index.ts"` unless `"declaration": true` is added to `tsconfig.base.json` repo-wide. If the consuming app is `apps/web`, either add the new package to `next.config.js`'s `transpilePackages` (lets Next.js compile it from source directly) or make sure whatever builds `apps/web` builds this package first via Turborepo's dependency graph (the `...` filter suffix).

**Before trusting any build "success":** a compile succeeding is not the same as the compiled output actually running. This session's core lesson — `tsc` reported success while `build-tolerant.js` correctly emitted output, and the resulting container still crashed on `node index.js` for an entirely separate reason. Always follow a successful build with an actual container start and a real health-check/GraphQL request, not just a green build log.

## Part 6 — `/settings/profile` static-export crash (Vercel build blocker)

The first real Vercel build failed with "Export encountered errors on following paths: /settings/profile" — identical to an earlier local Docker build failure, confirming this is a genuine code issue, not an environment fluke. The page (`apps/web/pages/settings/profile.tsx`) imports `Tab`, `ProfileForm`, `ProfilePicture`, `SnackbarProvider`/`useSnackbar`, and `PageWrapper` from `@luxgen/ui`. Each of those components was individually inspected — `PageWrapper`/`ProfilePicture`/`ProfileForm`/`Tab` all route through a shared `withSSR()` wrapper and guard any `window`/`document` access behind `typeof window !== 'undefined'` checks, and the page's own `document.querySelector`/`FileReader` calls are correctly scoped inside `onClick`/async handlers, not render-time code. No single throwing line was isolated from source inspection alone (the fuller stack trace from Vercel's build log, which would show the exact line, wasn't available).

Rather than keep hunting inside a large shared UI package for an elusive throw, the page was fixed at the Next.js level: `EditProfilePageContent` (renamed `EditProfilePageContentImpl`) is now wrapped with `next/dynamic(() => Promise.resolve(EditProfilePageContentImpl), { ssr: false })`. This is the standard, safe fix for a purely-interactive settings page with no SEO value — Next.js stops trying to statically pre-render it entirely (no static HTML is generated for this route at build time), while the page still behaves identically once hydrated in the browser, on Vercel or anywhere else. If the same "Export encountered errors" pattern shows up on another page later, apply the same fix there rather than re-deriving it.

**Local verification note:** this session's sandbox could not run the actual monorepo build to confirm end-to-end — the `turbo` native binary (`turbo-linux-arm64`) segfaults inside the sandbox's restricted execution environment, unrelated to any code change. What was verified instead: `tsc --noEmit` against `apps/api`'s own `tsconfig.json` produced exactly the same 43 pre-existing errors documented in Part 2 (zero new errors from any change in this session), and the same check against `apps/web` showed only pre-existing module-resolution noise that `next.config.js`'s `typescript.ignoreBuildErrors: true` already tolerates in the real build. The next actual `git push` / Vercel build is the real confirmation this is fixed.

## Part 7 — Cross-domain auth: the refresh-cookie gap (and why it was worse than first thought)

Investigating the `luxgen.in` (API) / `luxgen.shop` (dashboard) split surfaced a bigger issue than the known `sameSite` cookie risk: **the httpOnly refresh-token cookie was never being set by the login flow the frontend actually uses.** `apps/api/src/routes/auth.ts`'s REST `/login`/`/register`/`/refresh` endpoints correctly call `setRefreshCookie`, but the frontend's login page (`apps/web/pages/login.tsx`) authenticates via the GraphQL `login` mutation, not the REST route — and the GraphQL resolver (`apps/api/src/schema/user/resolvers.ts`) never called `setRefreshCookie` at all. Net effect: no refresh cookie was ever issued in practice, and nothing on the frontend ever called `POST /api/auth/refresh` either. Silent token renewal wasn't fragile — it was entirely wired up on the backend and entirely disconnected from the frontend.

Fixed with four coordinated changes:

`apps/api/src/utils/refreshToken.ts` — `refreshCookieOptions()` now sets `sameSite: isProd ? 'none' : 'lax'` (was hardcoded `'lax'`). Browsers never attach a `lax` cookie to a cross-site `fetch`/XHR (only to top-level navigations), and `luxgen.shop` calling `luxgen.in` is exactly that case. `'none'` requires `secure: true`, which was already conditional on `NODE_ENV === 'production'`. Also extracted `refreshPayloadFromUser()` as a shared export (it was a private, duplicated-in-spirit helper inside `routes/auth.ts`) so REST and GraphQL can't drift into building the refresh payload two different ways.

`apps/api/src/schema/user/resolvers.ts` — the `login` and `register` mutations now call `setRefreshCookie(ctx.res, refreshPayloadFromUser(result.user))` after a successful auth, mirroring the REST routes exactly. `GraphQLContext` already exposed `res` (Express `Response`), so this needed no plumbing changes.

`apps/web/lib/token-refresh.ts` (new) — `refreshAccessToken()` POSTs to the *relative* path `/api/auth/refresh` (not the absolute cross-domain API URL) with `credentials: 'include'`. The relative path matters: `next.config.js` already rewrites `/api/auth/:path*` to the real API host server-side, so from the browser's perspective this is a same-origin call — more robust than a direct cross-domain fetch, and it keeps working even if the `sameSite` fix above ever regresses. Concurrent 401s are de-duplicated behind a single in-flight promise so five simultaneous GraphQL calls trigger one refresh, not five races against the same rotating cookie. `revokeRefreshToken()` similarly calls `/api/auth/logout` so logout actually clears the server-side cookie, not just `localStorage`.

`apps/web/graphql/client.ts` — the Apollo `errorLink` no longer immediately logs the user out on every `session_expired` GraphQL error. It now attempts one silent `refreshAccessToken()` call first; on success it retries the original operation with the new Bearer token (via `operation.setContext` + `forward(operation)`), and only falls back to `clearStoredSession()` + redirect if the refresh itself fails (expired/invalid/missing refresh cookie). `tenant_mismatch`/`unauthorized` reasons are intentionally excluded from retry — those are real authorization failures, not expiry, and retrying would mask a permissions bug as a confusing login redirect.

**Still an ops step, not a code step:** the API's `CORS_ORIGIN` (or `CORS_ORIGINS`) value in SSM needs to actually be `https://luxgen.shop` (the dashboard's real origin) for any of this to work end-to-end. The CORS middleware itself (`apps/api/src/app.ts`) was already correct going into this session — it uses a proper origin-allowlist callback with `credentials: true`, never a wildcard `*` (which browsers reject outright when combined with credentials). Nothing to fix there; the SSM value just needs to match wherever the dashboard is actually deployed. This couldn't be applied from this environment (no AWS network access from the sandbox, documented in Part 8) — it's the one remaining manual step.

## Part 8 — Orchestrated deployment workflow (API + web, edge cases covered)

This is the end-to-end sequence for shipping a change that touches both apps, with the failure mode for each step and what catches it.

**1. Local/CI validation before anything ships.** Run `npm run build:api` and `npm run build:web` (or let CI do it via the GitHub Actions workflow). If either fails, stop — do not deploy the other half either, since the two apps' contracts (GraphQL schema, REST payload shapes, cookie names) are shared and a half-shipped change can silently break the deployed half.

**2. API deploy (EC2, via `scripts/deploy-api.sh`).** The script builds the new image before touching the running container, health-checks `http://localhost:4000/health`, and automatically retags `:previous` back to `:latest` and restarts on failure — never `docker compose up -d --build` directly. Edge case: if the health check passes but the *GraphQL* endpoint is actually broken (schema error, DB connection issue not surfaced by `/health`), the shallow health check won't catch it. Mitigation: extend the health check to also POST a trivial GraphQL query (e.g. `{ __typename }`) and require a 200 with a valid JSON body, not just a 200 from `/health`, before declaring the deploy successful.

**3. Web deploy (Vercel, automatic on push).** Vercel builds from `Root Directory = apps/web` with `Build Command = cd ../.. && npm run build:web`. Edge case: a Vercel preview deployment (on a PR) gets its own random `*.vercel.app` URL, which is neither `luxgen.shop` nor in the API's CORS allowlist — GraphQL calls from preview URLs will fail CORS by design. This is expected, not a bug; only the production deployment (bound to `luxgen.shop`) needs to be in `CORS_ORIGIN`.

**4. DNS + cookie + CORS must move together.** These three are coupled: whatever origin the dashboard is actually served from must (a) be the value in `CORS_ORIGIN`/`CORS_ORIGINS` on the API, and (b) be a domain the refresh cookie's `sameSite:'none'` setting is compatible with (any HTTPS origin works — `'none'` doesn't care which domain, only that the connection is secure). Edge case: if `luxgen.shop`'s DNS is repointed to Vercel but `CORS_ORIGIN` is still stale (e.g. still `luxgen.in`, the mistake this session nearly shipped before the two-domain intent was clarified), the dashboard will load fine but every GraphQL call will fail CORS with a browser console error, not a visible server error — this looks like "the site is broken" with no obvious cause in the Network tab's response (CORS failures are enforced client-side after the response arrives). Always re-check `CORS_ORIGIN` immediately after any DNS/domain change.

**5. Rollback.** API: `scripts/deploy-api.sh`'s automatic revert to `:previous` handles the common case; a manual `docker compose up -d api` after manually retagging is the fallback if the script itself can't run. Web: Vercel keeps every previous deployment; "Promote to Production" on the last-known-good deployment in the Vercel dashboard is an instant rollback, no rebuild needed. Neither rollback path depends on the other succeeding — the two apps are deployed and rolled back independently by design (this is why the Dockerfile was split into independent `builder-api`/`builder-web` targets in Part 1).

**6. Cache invalidation.** Vercel's CDN caches static assets and ISR pages by content hash automatically on each deploy — no manual cache-busting step needed for the web app. The one thing that does need manual attention: if a GraphQL schema field is renamed or removed, Apollo Client's `InMemoryCache` on already-open browser tabs will hold stale cached data referencing the old field shape until the user does a hard refresh; this is a normal Apollo consideration, not specific to this stack, and isn't solved by server-side deploy tooling.

**7. Auth-flow edge cases now covered by Part 7's fix.** Access token expires mid-session → silently refreshed via the httpOnly cookie, user never notices. Refresh cookie itself expired/revoked (30 days idle, or user logged out elsewhere) → refresh call returns 401 → user is cleanly logged out with the existing `session_expired` notice, no infinite retry loop (retry is attempted at most once per failed operation, gated by `operation.getContext().__refreshRetried`). Five tabs open, token expires while all five are active → one network call to `/api/auth/refresh`, not five, via the in-flight-promise de-dupe in `token-refresh.ts`. User explicitly logs out → both the local session and the server-side httpOnly cookie are cleared (`revokeRefreshToken()`), so the cookie can't be replayed after logout.
